# Remapping the commit citations after the history rewrite

Written 2026-08-12 against `fa7a4f0`. The repository's history was rewritten
with `git-filter-repo` to redact a student ID before first publication — the
decision that [`2026-08-12-public-release-audit.md`](2026-08-12-public-release-audit.md)
§1 put in front of the author as "option 2, free only right now". It was taken.
It also changed the SHA of every commit, and this project cites SHAs as
provenance throughout. This document records the repair.

The mapping is not guesswork: `git-filter-repo` left `.git/filter-repo/commit-map`,
172 old→new full-SHA pairs. Every citation in the tree resolved through it.

---

## 1. How citations were told apart from other hex

A naive `[0-9a-f]{7,40}` scan over all 206 tracked text files returns **787**
matches. Only 188 of those are commit citations. The separation was done in two
stages, and neither stage was a judgement call:

1. **599 of the 787 are pure decimal digits** — COCO annotation coordinates in
   `recog/realtest/annotations/instances_default.json`, timestamps, and figures
   in prose. None of them is a prefix of any commit in the old map or in the
   current history, so none is a citation.
2. **The remaining 188 all contain at least one `a`–`f` and all prefix-match
   either an old-map commit or a live one.** That is the discriminator that
   matters: a 7-hex-character string matching one of 172 known commits by
   chance is a roughly 1-in-10⁶ event, so a prefix hit is strong evidence, not a
   coincidence. There were **zero** letter-bearing hex strings that matched
   neither — i.e. no typos, no invented SHAs, no citations to commits that never
   existed.

Two further checks came back empty:

- **Uppercase.** No `[0-9A-F]{7,40}` citation anywhere; the convention is
  uniformly lowercase.
- **Length.** All 188 are exactly **7 characters**. There is no 8-, 10- or
  40-character citation in the tree, so "preserve the citation's length
  convention" was satisfied by construction.

The two tracked PDFs (`docs/FDR_v2.pdf`, `docs/FDR_v3.pdf`) were checked and are
**not affected**: both were last written at the baseline commit (`69fad79`,
2026-08-05), which predates every SHA citation in `FDR_v3.md`. They cannot
contain a citation that the rewrite invalidated. (Their text is font-encoded and
not extractable as plain text, so this was established from history rather than
from content — but the history argument is conclusive.)

## 2. Safety of the substitution

Three properties were verified before any file was written:

| Check | Result |
| --- | --- |
| Does each cited 7-char prefix identify exactly one old commit? | Yes, all 188. No ambiguous prefix. |
| Does each replacement 7-char prefix identify exactly one *current* commit? | Yes, all 188. **0 ambiguities.** |
| Does the map drop or merge any commit (all-zero target, duplicate target)? | No. 172 distinct targets, all present in the current history. |
| Could a replacement collide with a SHA already in the same file? | No. No citation prefix-matches both an old-map commit and a live one, so substitution is single-pass and order-independent. |

The mapping is also corroborated *semantically*, which is the check that would
have caught a corrupted map. Every remapped target's commit subject matches the
claim the prose makes about it — `d6c46ac` "lifted the packing ceiling" →
`562ca75` `fix(plan): lift the packing ceiling`; `dedf700` "fixed best-only
saving" → `0ac6c5b` `fix(training): always save last.pt, not only the best
epoch`; `ac54743` "one authoritative 18650 dimension" → `f4596e8` of exactly
that name. All 31 doc-cited pairs were read this way and all 31 agree.

Commit *ranges* survive too: the only range cited, `27cbd97..9fcf136` (the
tray-interior fix), maps to `a31ac28..043e92d`, and `git merge-base --is-ancestor`
confirms the new pair is still ancestor-ordered.

## 4. What was deliberately *not* changed

Nothing was left dangling because it could not be mapped. **Every citation in
the repository maps cleanly.** 39 were left alone because the brief for this
work forbids editing those files, not because the mapping is in doubt. They are
listed here in full so the remaining work is mechanical rather than a fresh
investigation.

### 4a. 22 citations in 11 receipts — cannot be truthfully repaired here

Every `docs/receipts/seg_eval*.txt` carries, at line 27, the note
`(real tray-wall geometry, commits 27cbd97..9fcf136)`. Both SHAs are dead.

They are not receipt *headers*; they are inside the generated body, and the
string is emitted by `recog/seg_evaluate.py:778`. Hand-editing the receipt would
make it disagree with the tool that produced it — a receipt that no longer
matches its generator is worse than one with a stale SHA, because the first
defect is invisible and the second is not. **The honest repair is to fix the
source string and regenerate the receipts**, which requires a code change and a
GPU run, both out of scope here. Recorded, not faked.

## 6. One thing the rewrite did not cause

`docs/receipts/git-log.txt` is not a git log. It reads, in full:

> `[No git history available — project was developed outside a versioned`
> `workspace in this session. In the assessed submission, git log --oneline is`
> `expected to show the sprint-by-sprint progression referenced in FDR §12.1…]`

That receipt was a placeholder before the rewrite and is one after it. FDR §12.1
points at commit-by-commit progression as evidence of process, and the receipt
that is supposed to *be* that evidence has never contained any. This is a real
gap in the provenance chain that predates the redaction entirely, and the
rewrite neither caused it nor makes it worse — but it is now the only remaining
place where a reader is pointed at commit history and handed nothing.
Regenerating it is a one-line `git log --oneline > docs/receipts/git-log.txt`,
and it would now be truthful. Flagged, not done: it is a receipt, and this brief
does not change receipt content.

A second, smaller instance of the same class: `docs/FDR_v3.pdf` was last written
at the baseline commit and does not contain any of the SHA citations that
`FDR_v3.md` has accumulated since. The PDF is a stale export, not a wrong one —
but "`FDR_v3.pdf` is the same document as submitted" in `docs/README.md` is
doing quiet work there, and the two are no longer the same document.
