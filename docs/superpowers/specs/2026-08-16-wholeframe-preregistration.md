## 1. The question

`docs/superpowers/specs/2026-08-06-segmentation-placement-area-design.md` §3.1 chose a
per-ROI segmenter over the FDR's proposed Mask R-CNN head, and rejected whole-frame
semantic segmentation in the same section. But the whole-frame design it rejected was
**whole-frame + connected-component instance recovery**, on the ground that connected
components reintroduce the occlusion failure mode FDR §10.6 attributes 22% of heuristic
detector misses to.

That objection does not apply to the arm tested here, which keeps the detector for
instance identity and uses the whole-frame model only for pixel labels. §3.1 therefore
has **no measured basis for rejecting this particular alternative**, and this spec
supplies one.

## 2. What is actually being compared

| | ROI arm (ships) | Whole-frame arm |
|---|---|---|
| Input | one 256² crop per detected cartridge | one 512² frame |
| Cost | 2.3 ms × n_cartridges | fixed |
| Cartridge sampled at | ≈ native crop resolution | ≈ 0.4× native |
| Instance identity | detector box | detector box (unchanged) |
| Everything downstream | identical | identical |

Both arms are scored by `recog.seg_evaluate.evaluate` on the **same validation crops**,
with the same ground truth, the same per-frame scales and the same metric code. The only
difference is the prediction step — `predict_val_crops` against
`predict_val_crops_from_frames`.

## 3. The leak, and how it is prevented

The whole-frame arm trains on frames; the comparison scores crops. A frame in whole-frame
training could contain a crop in the shared validation set, and the whole-frame model
would then be scored on pixels it had trained on.

`recog.seg_wholeframe.frame_split_from_crop_split` derives the frame split from the crop
split: a frame is a training frame only when **every** crop it carries is in the crop
split's training half. Any frame contributing even one validation crop is held out
entirely.

This is asymmetric, and deliberately so — it can only move frames *out* of whole-frame
training, so it handicaps the arm being tested rather than the incumbent.

**Verification before any result is quoted:** the intersection of whole-frame training
frames with the source frames of the 126 validation crops must be **empty**. If it is not,
this comparison is void.

## 4. The prediction

> Whole-frame `bay` boundary displacement will exceed the ROI arm's **1.226 mm** by
> **≥ 0.5 mm** on the same validation split — i.e. it will read ≥ 1.726 mm.

**Resolvable effect: 0.5 mm.** Chosen, and not fitted, from what the number is for: a
28×28 Mask R-CNN head over this corpus quantises at 4.68 px, and the ROI arm's 3.14×
margin against that is the measurement §3.1 rests on. An extra 0.5 mm cuts that margin to
about 2.2×. Below that the whole-frame arm stops being clearly better than the option
already rejected, which is the threshold that matters.

**Secondary, not thresholded, reported either way:** pooled `bay` IoU; per-class IoU for
`electronics` and `obstruction`; wall-clock per frame against the 50 ms budget.

## 5. The falsifier

> If whole-frame comes within **0.25 mm** of 1.226 mm *and* runs in **≤ 40 ms** per frame,
> the prediction is refuted.

In that case §3.1's rejection of whole-frame is **scale-dependent only** — true for the
1–8 cartridges this corpus carries, false in general — and §3.1 must be amended to say so
rather than left standing.

The crossover is arithmetic and is stated now so it cannot be reverse-engineered later:
ROI costs 2.3 ms per cartridge, whole-frame is fixed at roughly 33 ms at native
resolution, so they cross at **≈ 14 cartridges per frame**. Any claim that per-ROI is
better *in general* is wrong above that count regardless of how this experiment lands.

## 6. Failure modes that would void the result

Named in advance so none of them can become a post-hoc explanation for a bad number.

1. **Class imbalance.** On a whole frame, cartridges are a small fraction of the pixels,
   so `bay` is rarer than in a crop and cross-entropy is dominated by background harder.
   `dice_weight` is left at 0.5 anyway — changing two things at once ends the comparison.
   If the arm loses **specifically** on the rare classes while `cartridge` holds up,
   reweighting is the named follow-up and must be reported as a **second arm**, not as
   this one re-run.
2. **Learning rate.** Scaled linearly with the batch size (8 → 2, so 0.01 → 0.0025). Not
   tuned and not claimed as tuned. A sweep is a named follow-up.
3. **Resolution floor.** 512 is a budget choice, not the architecture's ceiling. If 512
   loses badly, a native 1280×720 run is a **separate arm**.
4. **Convergence.** If the whole-frame arm's training loss has not flattened by epoch 40,
   the result is reported as *inconclusive*, not as a loss.

## 7. What gets published either way

Both outcomes go into the repository at the same prominence, as the three existing nulls
did.

- **Prediction holds** — §3.1's conclusion is confirmed *by measurement* for the first
  time, and its stated reason (connected components) is replaced by the real one
  (resolution per object at this scale).
- **Prediction refuted** — §3.1 is amended, the README's architecture rationale is
  amended, and the honest claim becomes that per-ROI was right for this corpus and not in
  general.
- **Inconclusive** — recorded as inconclusive. It is not re-run until it produces a
  publishable direction.

## 8. Commands

```bash
# train the whole-frame arm
python -m recog.seg_training --config configs/wholeframe_segmentation.yaml

# score both arms on the same crops, same metrics, same split
python scripts/eval_wholeframe.py \
    --roi-checkpoint recog/checkpoints/seg/best.pt \
    --wholeframe-checkpoint recog/checkpoints/seg_wholeframe/best.pt \
    --out docs/receipts/wholeframe_comparison.txt
```
